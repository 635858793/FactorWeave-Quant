# 数据库迁移说明文档

## 迁移策略说明

### 为什么使用 `move` 而非 `copy`？

我们选择使用 `shutil.move()` 而非 `shutil.copy2()` 进行数据库迁移，原因如下：

#### ✅ 优势对比

| 特性 | copy (复制) | move (移动) | 说明 |
|-------|------------|-------------|------|
| **磁盘空间** | 需要双倍空间 | 无额外空间需求 | 避免磁盘空间不足 |
| **数据完整性** | 复制中断可能损坏数据 | 原子性操作 | move 要么完全成功，要么完全失败 |
| **速度** | 慢（需要完整复制） | 快（仅更新文件系统元数据） | 大文件移动更快 |
| **权限问题** | 可能遇到权限错误 | 更少权限问题 | 移动操作权限要求更低 |
| **并发安全** | 复制期间数据库锁定 | 移动时间极短 | 减少数据库锁定时间 |
| **事务性** | 无 | 原子性 | 操作不可分割 |

#### 🚫 copy 方式的问题

1. **磁盘空间不足**
   - 假设数据库文件 10GB
   - copy 需要额外 10GB 空间
   - 如果磁盘只有 12GB 可用空间，迁移会失败

2. **复制中断风险**
   - 大文件复制过程中断电/崩溃
   - 可能导致目标文件不完整
   - 需要手动清理部分文件

3. **性能问题**
   - 复制 10GB 文件可能需要几分钟
   - 复制期间数据库不可用
   - 影响系统正常运行

4. **权限复杂性**
   - 需要源文件读权限
   - 需要目标目录写权限
   - 需要目标文件写权限

#### ✅ move 方式的优势

1. **空间高效**
   - 仅更新文件系统元数据
   - 不需要额外磁盘空间
   - 适合任何大小的数据库

2. **原子性保证**
   - 操作要么完全成功，要么完全失败
   - 不会出现部分迁移的情况
   - 数据完整性有保障

3. **快速执行**
   - 移动 10GB 文件只需毫秒级
   - 数据库停机时间极短
   - 对系统影响最小

4. **简单可靠**
   - 只需要源目录删除权限
   - 只需要目标目录创建权限
   - 操作逻辑简单，不易出错

## 备份策略

### 自动备份（默认启用）

迁移脚本会自动创建备份：

```bash
# 备份目录命名规则
backup/db_migration_YYYYMMDD_HHMMSS/

# 示例
backup/db_migration_20260101_120000/
```

### 备份内容

- 所有被迁移的数据库文件
- 保留原始文件名
- 保留完整的目录结构

### 清理备份

确认迁移成功后，可以清理备份：

```bash
# 删除特定备份
rm -rf backup/db_migration_20260101_120000/

# 删除所有迁移备份
rm -rf backup/db_migration_*/
```

## 常见问题

### Q1: 迁移失败怎么办？

**A**: 检查以下几点：

1. **数据库文件被占用**
   ```bash
   # 检查是否有进程在使用数据库
   # Windows: 使用 Process Explorer
   # Linux: 使用 lsof
   lsof enhanced_async_tasks.db
   ```

2. **权限不足**
   ```bash
   # 检查文件权限
   ls -la enhanced_async_tasks.db
   
   # 修改权限（如需要）
   chmod 644 enhanced_async_tasks.db
   ```

3. **目标目录已存在**
   ```bash
   # 删除或重命名目标文件
   rm data/enhanced_async_tasks.sqlite
   # 或
   mv data/enhanced_async_tasks.sqlite data/enhanced_async_tasks.sqlite.bak
   ```

### Q2: 迁移后系统无法启动？

**A**: 检查配置：

1. **确认数据库路径已更新**
   - 检查 `enhanced_async_manager.py` 中的默认路径
   - 检查 `init_database_and_tables.py` 中的数据库列表

2. **检查数据库文件完整性**
   ```bash
   # SQLite 数据库
   sqlite3 data/enhanced_async_tasks.sqlite "SELECT count(*) FROM async_tasks;"
   
   # DuckDB 数据库
   duckdb data/kline_stock.duckdb "SELECT count(*) FROM information_schema.tables;"
   ```

3. **查看日志**
   ```bash
   # 检查系统启动日志
   tail -f logs/system.log
   ```

### Q3: 如何回滚迁移？

**A**: 使用备份文件：

```bash
# 1. 停止系统

# 2. 恢复备份
cp backup/db_migration_20260101_120000/enhanced_async_tasks.db \
      enhanced_async_tasks.db

# 3. 恢复代码配置
# 使用 git 回滚或手动恢复配置文件

# 4. 重启系统
```

### Q4: 迁移过程中断电怎么办？

**A**: 使用 move 操作的优势：

- **如果移动未完成**: 文件仍在原位置，系统可正常启动
- **如果移动已完成**: 文件已在新位置，系统可正常启动
- **不会出现**: 文件部分在新位置、部分在旧位置的情况

## 最佳实践

### ✅ 推荐做法

   - 停止所有应用

   - 检查磁盘空间

4. **不要**删除备份（直到确认成功）

## 技术细节

### shutil.move() 的工作原理

```python
# 同一文件系统内
shutil.move(src, dst)
# 等价于: os.rename(src, dst)
# 仅更新文件系统元数据，不移动实际数据

# 跨文件系统
shutil.move(src, dst)
# 等价于: copy + remove
# 会先复制，再删除源文件
```

### 原子性保证

```python
# 文件系统保证
try:
    shutil.move(src, dst)
    # 要么完全成功
    # 要么完全失败（抛出异常）
    # 不会出现部分移动的情况
except Exception as e:
    # 源文件仍在原位置
    # 目标文件不存在或完整
    # 可以安全重试
```

## 总结

使用 `move` 而非 `copy` 进行数据库迁移是明智的选择：

✅ **更安全**: 原子性操作，数据完整性有保障  
✅ **更快速**: 毫秒级完成，对系统影响最小  
✅ **更高效**: 不需要额外磁盘空间  
✅ **更可靠**: 操作逻辑简单，不易出错  

**建议**: 在生产环境迁移时，始终使用 `move` 方式，并启用备份功能。
