# 核心未实现功能开发计划与实施路线图

## 一、概述

本文档基于对 Hikyuu-UI 系统的深度分析，制定了针对三大核心未实现功能模块的真实可实施开发计划。分析范围涵盖 AI 选股服务、风险管理和分布式服务三大模块，重点解决系统中普遍存在的 `raise NotImplementedError` 和 TODO 标记问题。

开发计划遵循分阶段实施原则，将工作分解为短期（1-2 周）、中期（1 个月）和长期（3 个月）三个阶段。每个阶段都设有明确的里程碑、交付物和验收标准，确保开发工作有序推进并可追踪。

## 二、AI 选股服务开发计划

### 2.1 依赖关系分析

AI 选股服务（AIStockSelector）是实现智能股票筛选的核心组件，其依赖关系和集成点已明确。服务在 `api_server.py` 的 `/api/ai-select-stocks` 端点中被实例化并调用 `select_stocks` 方法，这表明 API 层与业务逻辑层已建立基本连接。

系统已定义多种 AI 模型类型作为技术储备，包括 LSTM 神经网络、GRU 循环神经网络、XGBoost 梯度提升树、Random Forest 随机森林、SVM 支持向量机以及 DNN 深度神经网络。这些模型定义位于 `model_profiles.py` 文件中，提供了模型选择和配置的基础架构。

当前的主要障碍在于 `__init__` 方法中的模型初始化逻辑标记为 TODO，尚未实现实际的模型加载和训练流程。`select_stocks` 方法依赖模型初始化结果，而 `explain_selection` 方法用于解释选股理由，同样需要模型推理结果作为输入。

### 2.2 集成方案设计

AI 选股服务的集成方案采用分层架构设计，分为数据层、模型层和服务层三个层次。数据层负责获取和处理股票数据，模型层负责加载和执行 AI 模型推理，服务层负责提供统一的选股接口。

数据层的实现依赖 StockService 和 DataAccess 组件。StockService 提供了 `get_stock_data` 方法获取股票历史数据，`get_stock_list` 方法获取股票列表，`_get_stock_realtime_data` 方法获取实时数据。DataAccess 提供了 `get_kline_data` 方法获取 K 线数据，`get_latest_price` 方法获取最新价格。这些组件构成了 AI 选股服务的数据基础。

模型层的实现需要基于系统中已定义的 AI 模型类型和智能模型选择机制。首先实现基础的机器学习选股模型，支持 XGBoost 和 Random Forest 两种模型类型；然后扩展到深度学习模型，支持 LSTM 和 GRU 两种循环神经网络；最后实现模型选择和参数调优功能。模型配置文件采用 YAML 格式，支持模型类型、超参数和特征工程参数的配置。

服务层的实现需要提供统一的选股接口，支持按模型类型、选股数量和风险偏好等参数进行股票筛选。服务层还需要实现选股结果的可解释性分析，解释每个选中股票的关键因子和筛选原因。

### 2.3 实施步骤

第一阶段（1-3 天）实现数据层集成。首先完成 StockService 的依赖注入，确保 AI 选股服务能够获取股票数据；然后实现数据预处理流水线，支持数据清洗、特征工程和数据标准化；最后实现特征提取功能，支持技术因子、基本面因子和情绪因子的提取。

第二阶段（4-7 天）实现模型层集成。首先实现 XGBoost 选股模型，支持分类和回归两种任务类型；然后实现 Random Forest 选股模型，支持特征重要性分析；最后实现模型训练和评估功能，支持交叉验证和回测验证。

第三阶段（8-14 天）实现服务层集成。首先实现统一的选股接口，支持多模型组合选股；然后实现可解释性分析功能，解释选股原因和关键因子；最后实现 API 端点集成，对接 `/api/ai-select-stocks` 接口。

## 三、风险管理器开发计划

### 3.1 依赖关系分析

风险管理器（RiskManager）是风控系统的核心组件，负责检查交易信号的风险并做出风控决策。当前版本存在两个关键方法未实现：`_load_risk_params` 方法负责从配置文件加载风险控制参数，`get_current_price` 方法负责获取指定股票的实时价格。

风险管理器的集成点分布在两个位置：`unified_performance_widget.py` 用于展示投资组合的风险指标，`risk_control_center_tab.py` 用于风控中心的实时监控。这两个集成点都依赖 RiskManager 提供的风险检查功能，确保交易决策符合风控要求。

系统中已有丰富的风控相关组件可以作为依赖基础。DataAccess 提供了 `get_latest_price` 方法获取最新价格，StockService 提供了 `_get_stock_realtime_data` 方法获取实时数据（价格、成交量、换手率等），配置管理系统支持 YAML 格式的配置文件加载。这些现有组件为 RiskManager 的实现提供了坚实基础。

此外，系统还存在多个风控相关的辅助组件，包括 `risk_control.py` 中的 RiskMonitor 类、`risk_alert.py` 中的 RiskAlertSystem 类、`risk_evaluation.py` 中的 RiskEvaluator 类、`risk_agent.py` 中的 RiskAssessmentAgent 类以及 `advanced_risk_control_service.py` 中的高级风控服务。这些组件提供了风险监控、告警、评估和高级风控功能，可以与 RiskManager 形成互补。

### 3.2 集成方案设计

风险管理器的集成方案采用配置驱动和组件复用两个核心原则。配置驱动原则要求风控参数通过配置文件定义，支持动态加载和热更新；组件复用原则要求优先使用现有组件，避免重复开发。

`_load_risk_params` 方法的实现需要支持 YAML 格式的配置文件加载。配置文件结构包括最大持仓比例（max_position_size）、单个股票最大持仓比例（max_single_position）、止损比例（stop_loss）和最大回撤限制（max_drawdown）等核心参数。配置加载逻辑需要支持默认配置、用户配置和环境配置的优先级管理，支持配置热更新和配置验证功能。

`get_current_price` 方法的实现需要优先使用 DataAccess 提供的 `get_latest_price` 方法作为数据源。当 DataAccess 不可用时，回退到 StockService 的 `_get_stock_realtime_data` 方法获取实时数据。方法需要实现价格缓存、错误处理和超时控制机制，确保风控检查的实时性和可靠性。

风控检查逻辑的实现需要整合 `_check_position_limit`、`_check_stop_loss` 和 `_check_drawdown` 三个子方法。`_check_position_limit` 方法检查交易信号是否符合持仓限制要求；`_check_stop_loss` 方法检查持仓是否触发止损条件；`_check_drawdown` 方法检查当前回撤是否超过最大回撤限制。

### 3.3 实施步骤

第一阶段（1-2 天）实现配置文件加载。首先设计风控参数配置文件的 YAML 格式规范，包括参数类型、默认值和取值范围；然后实现 `_load_risk_params` 方法，支持配置文件加载和参数验证；最后实现配置热更新功能，支持在不重启服务的情况下更新风控参数。

第二阶段（3-4 天）实现价格获取功能。首先实现 `get_current_price` 方法，集成 DataAccess 的价格获取能力；然后实现价格缓存机制，减少数据访问频率；最后实现错误处理和超时控制，确保方法的健壮性。

第三阶段（5-7 天）实现风控检查整合。首先优化 `_check_position_limit`、`_check_stop_loss` 和 `_check_drawdown` 三个子方法的实现；然后实现风控检查的组合逻辑，支持多种风控规则的联合检查；最后对接集成点，完成 `unified_performance_widget.py` 和 `risk_control_center_tab.py` 的风控功能集成。

## 四、分布式服务开发计划

### 4.1 依赖关系分析

分布式服务（DistributedService）是实现分布式回测和任务分发的关键组件，负责管理计算节点、分发任务和收集结果。当前版本的主要问题是回测引擎集成不完整，导致 `_execute_backtest_task` 方法返回待集成状态。

分布式服务的集成点分布在三个位置：`import_execution_engine.py` 中的 `_init_distributed_service` 方法负责初始化分布式服务，`unified_data_import_engine.py` 中可能存在类似的初始化逻辑，`service_bootstrap.py` 中的 `create_distributed_service` 函数负责创建分布式服务实例。这三个集成点表明分布式服务需要与数据导入和服务引导流程紧密配合。

分布式服务依赖以下核心组件：UnifiedBacktestEngine 用于执行分布式回测任务，AnalysisService 用于执行分布式分析任务，AIPredictionService 用于执行分布式优化任务。HTTP Bridge（DistributedHTTPBridge）用于节点间的通信和任务分发。

从代码分析可以看出，分布式服务已实现大部分基础设施功能，包括节点发现（NodeDiscovery）、任务调度（TaskScheduler）、任务队列管理、节点管理和负载均衡等。主要缺失的是与业务引擎（回测引擎、分析引擎、优化引擎）的集成。

### 4.2 集成方案设计

分布式服务的集成方案采用分层集成和渐进式增强两个核心原则。分层集成原则要求按照基础设施层、服务层和业务层的顺序逐步集成；渐进式增强原则要求先实现核心功能，再逐步添加高级特性。

与 UnifiedBacktestEngine 的集成是首要任务。集成方案需要解决以下问题：首先是引擎实例化问题，确定 UnifiedBacktestEngine 的构造函数参数和依赖注入方式；其次是任务参数映射问题，将 DistributedTask 的 task_data 映射为回测引擎所需的参数；然后是执行结果解析问题，将回测引擎的返回结果转换为 DistributedService 统一的结果格式；最后是错误处理和超时控制问题，确保分布式回测的可靠性和可观测性。

与 AnalysisService 的集成是次要任务。从代码分析可以看出，AnalysisService 的集成已部分实现，分布式服务能够检测服务是否注册并返回相应的状态信息。进一步的工作需要完善服务调用参数的映射和结果解析。

与 AIPredictionService 的集成是增强任务。集成方案需要支持参数优化任务的分布式执行，利用遗传算法或贝叶斯优化等方法进行参数搜索，提高优化效率。

HTTP Bridge 的增强是基础设施任务。需要完善分布式通信协议，支持任务状态的实时同步和结果的流式传输，提高分布式服务的可用性和性能。

### 4.3 实施步骤

第一阶段（1-3 天）实现回测引擎集成。首先研究 UnifiedBacktestEngine 的 API 文档和使用示例，确定接口参数和返回格式；然后修改 `_execute_backtest_task` 方法，实现真实的回测任务执行；最后测试集成效果，验证分布式回测功能的可用性。

第二阶段（4-6 天）实现分析引擎集成。首先研究 AnalysisService 的 API 接口，确定参数格式和返回格式；然后完善 `_execute_analysis_task` 方法，实现真实的分析任务执行；最后优化任务调度逻辑，支持分析任务的负载均衡和优先级调度。

第三阶段（7-10 天）实现优化引擎集成。首先研究 AIPredictionService 的优化功能，确定参数优化任务的接口；然后实现 `_execute_optimization_task` 方法，支持分布式参数优化；最后实现优化结果的收集和展示功能。

第四阶段（11-14 天）完善基础设施。首先完善 HTTP Bridge 的通信协议，支持任务状态的实时同步；然后实现任务超时控制和错误重试机制；最后优化节点发现和负载均衡算法，提高分布式服务的性能和可靠性。

## 五、验收标准与里程碑

### 5.1 短期里程碑（1-2 周）

第一周结束时的验收标准包括：AI 选股服务能够加载 XGBoost 和 Random Forest 两种模型，能够根据模型筛选股票并返回结果；风险管理器能够从配置文件加载风控参数，能够获取股票实时价格，能够执行基本的风险检查；分布式服务能够执行真实的回测任务，返回正确的回测结果。

第二周结束时的验收标准包括：AI 选股服务能够解释选股原因和关键因子，能够对接 API 接口 `/api/ai-select-stocks`；风险管理器能够对接 `unified_performance_widget.py` 和 `risk_control_center_tab.py`，能够实时监控风险状态；分布式服务能够执行真实的分析任务，任务调度和节点管理功能正常。

### 5.2 中期里程碑（1 个月）

月末验收标准包括：AI 选股服务支持 LSTM 和 GRU 两种深度学习模型，模型选择和参数调优功能正常；风险管理器支持配置热更新和参数动态调整，风控告警功能正常；分布式服务支持分布式优化任务，HTTP Bridge 通信功能正常；系统整体的风控、选股和回测功能形成闭环。

### 5.3 长期里程碑（3 个月）

季度末验收标准包括：AI 选股服务支持所有定义的模型类型（6 种），可解释性分析功能完整；风险管理器支持高级风险指标（VaR、CVaR、熵风险等），风控策略可配置；分布式服务支持完整的分布式计算框架，节点发现和负载均衡功能健壮；系统完成所有 P0 和 P1 优先级的未实现功能开发，技术债务显著减少。

## 六、风险与应对措施

### 6.1 技术风险

第一个技术风险是 UnifiedBacktestEngine API 不稳定。如果 UnifiedBacktestEngine 的接口发生变化，可能导致已实现的集成代码失效。应对措施是采用适配器模式实现集成层，将业务逻辑与引擎接口解耦；建立接口版本管理机制，记录引擎 API 的变更历史；在集成代码中添加详细的错误日志，便于问题定位和修复。

第二个技术风险是模型训练资源消耗过大。AI 模型的训练需要大量计算资源，可能影响系统其他功能的正常运行。应对措施是采用异步训练模式，利用分布式服务进行模型训练；实现训练任务的优先级调度，确保关键任务优先获得资源；添加资源监控和限制功能，防止训练任务占用过多系统资源。

### 6.2 进度风险

第一个进度风险是需求变更导致返工。在开发过程中，业务需求可能发生变化，导致已实现的代码需要修改。应对措施是在开发初期与业务方充分沟通，明确需求范围和验收标准；采用敏捷开发方法，将工作分解为多个短周期迭代；保持代码的模块化和可测试性，降低变更带来的影响。

第二个进度风险是依赖组件未就绪。某些功能的实现依赖其他组件的就绪，如果依赖组件延迟交付，可能影响整体进度。应对措施是提前识别组件依赖关系，优先处理无依赖或低依赖的任务；建立组件就绪状态的监控机制，及时发现和处理依赖问题；准备备用方案，当依赖组件不可用时能够快速切换。

### 6.3 质量风险

第一个质量风险是代码缺陷影响系统稳定性。新开发的代码可能存在缺陷，影响系统的稳定性。应对措施是建立代码审查机制，所有代码变更必须经过审查才能合并；编写单元测试和集成测试，确保代码功能正确；添加监控和告警机制，及时发现和处理运行时错误。

第二个质量风险是性能不满足预期。新开发的功能可能存在性能问题，影响用户体验。应对措施是在开发过程中进行性能测试，及时发现和优化性能瓶颈；建立性能基准和监控指标，持续跟踪性能变化；优化关键路径代码，确保核心功能的响应时间满足要求。

## 七、资源需求

### 7.1 人力资源

短期开发需要投入 2 名后端开发工程师，分别负责 AI 选股服务和风险管理器的开发。分布式服务的开发需要投入 1 名后端开发工程师和 1 名架构师，架构师负责技术方案设计和代码审查。

中期开发需要维持 2-3 名开发人员的投入，重点是功能完善和性能优化。长期开发可以根据需要调整人员配置，重点是新功能开发和技术债务清理。

### 7.2 计算资源

模型训练需要 GPU 计算资源支持，建议配置 1 台配备 NVIDIA GPU 的服务器用于模型训练和推理测试。分布式服务测试需要多台计算节点，建议配置 3-5 台服务器用于分布式功能测试。

### 7.3 测试资源

功能测试需要准备测试数据和测试环境，建议建立独立的测试环境，避免影响生产环境。性能测试需要准备压力测试工具和监控工具，建议使用 JMeter 或 Locust 进行压力测试。

## 八、总结

本文档制定了针对 AI 选股服务、风险管理和分布式服务三大核心模块的开发计划。开发计划遵循分阶段实施原则，将工作分解为短期（1-2 周）、中期（1 个月）和长期（3 个月）三个阶段，每个阶段都设有明确的里程碑和验收标准。

开发计划的核心策略是依赖现有组件、采用配置驱动、实现渐进式增强。通过复用 DataAccess、StockService 等现有组件，避免重复开发；通过配置管理实现风控参数的动态调整，提高系统灵活性；通过分层集成逐步完善功能，降低开发风险。

实施本开发计划需要投入约 2-3 名开发人员，历时 3 个月完成。完成后，系统将消除大部分高优先级的未实现功能，核心技术债务显著减少，核心业务功能（AI 选股、风险控制、分布式回测）形成闭环。
