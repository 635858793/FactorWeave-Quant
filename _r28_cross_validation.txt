【声称 8】akshare_wrapper.py — 双重延迟 Bug
────────────────────────────────────────────────────────────────
文件: plugins/data_sources/utils/akshare_wrapper.py (共 191 行)
判定: ✅ 确认

精确位置:

  第一次延迟 — _apply_rate_limit()（第 83-97 行）:
    L83   def _apply_rate_limit(self):
    ...
    L92       if elapsed < min_interval:
    L93           wait_time = min_interval - elapsed + random.uniform(...)
    L95           time.sleep(wait_time)                        ← 第一次 sleep

  第二次延迟 — __getattr__ 包装器（第 115-126 行）:
    L115      def wrapper(*args, **kwargs):
    L116          self._apply_rate_limit()                      ← 调用第一次延迟
    L120          if self.enable_anti_crawler:
    L121              apply_anti_crawler_delay(self.min_delay,  ← 调用第二次延迟
    L122                                       self.max_delay)

  apply_anti_crawler_delay 定义于 retry_helper.py 第 164-165 行:
    L164  delay = random.uniform(min_delay, max_delay)
    L165  time.sleep(delay)                                    ← 第二次 sleep

特征: 这两次延迟是叠加的，总延迟 = delay1 + delay2。
      默认配置 min_delay=0.5, max_delay=2.0，每次请求叠加后
      最大可能等待约 4 秒，对批量下载场景影响极大。

严重度: 高 — 5000只股票 × ~2-4秒/次 ≈ 3-6小时额外延迟开销。

五、真实有效问题（按严重度排序）
================================================================================

  P0 (高):
  1. akshare_wrapper.py 双重延迟 — 每次请求叠加 2×sleep(),
     5000只股票场景下累计延迟可达数小时。修复: 删除 apply_anti_crawler_delay()
     或 _apply_rate_limit() 中的任一个。

  2. duckdb_operations.py execute_query() 绕过连接池 — 每次查询新建连接，
     高频场景下连接创建/销毁开销显著。修复: 改为使用 self.connection_manager
     获取连接（与同文件 query_data() 保持一致）。

  P1 (中):
  3. stock_service.py perform_advanced_search() N+1 查询 — 对每只股票
     调用 _get_stock_realtime_data()。修复: 改为批量获取实时数据接口
     或使用缓存预加载。

  P2 (低/待验证):
  4. enhanced_duckdb_data_downloader.py 批间串行 — 批次间确实串行等待，
     但批内使用 asyncio.gather 并发，实际瓶颈在数据源延迟（见 P0-1）。
     修复: 可考虑多批次并发执行，但需先修复双重延迟问题。
